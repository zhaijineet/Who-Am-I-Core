# 冰/火器官体系完整设计文档

## 设计审查问题解决记录（v1.1）

本版本解决了以下严重问题，确保设计符合项目范围约束：

### 已解决问题1：局部温度计算逻辑歧义 ✓
**原问题**：周围3×3范围在胸腔网格中的计算方式未明确定义

**解决方案**：
- 明确胸腔网格为 **2D 网格结构**（非3D）
- 采用 **曼哈顿距离**（Manhattan Distance）定义相邻关系
- 标准范围：曼哈顿距离 ≤ 1（等效3×3网格）
- 边缘器官自然计算实际存在的器官，无需特殊处理
- 详细说明见：[2.3 局部温度](#23-局部温度)

### 已解决问题2：温度状态判定循环依赖 ✓
**原问题**：同时使用全局温度和局部温度判定状态，存在循环依赖

**解决方案**：
- 采用 **五层判定架构**，确保单向数据流：
  1. 全局温度计算（基础数据）
  2. 全局温度修正（特殊器官）
  3. 器官状态判定（只基于全局温度）
  4. 局部温度计算（不影响状态）
  5. 最终效率计算（基础状态 × 局部修正）
- 局部温度只提供属性修正，不改变器官状态
- 详细说明见：[2.5.1 温度判定优先级](#251-温度判定优先级避免循环依赖)

### 已解决问题3：Malkuth机制复杂度过高 ✓
**原问题**："重写所有冰火器官局部温度"可能需要修改CCB核心代码

**解决方案**：
- 重新设计为 **"温度平衡加成"** 系统
- 不修改任何 CCB 器官数据，通过 API 层面包裹逻辑
- 使用"有效温度"概念，在实际温度外层应用修正
- 完全在 Who-Am-I-Core 工作区内实现，无需CCB API扩展
- 详细说明见：[3.4.1 Malkuth（王国）](#341-malkuth王国malkuth)

### 技术实现保证
- 所有温度计算通过 `TemperatureSystem` API 封装
- 单向数据流：器官层 → 温度系统层 → 数据层
- 缓存机制确保性能，避免运行时重复计算
- 详细 API 设计见：[6.1.1 温度系统API设计](#611-温度系统api设计)

## 1. 系统概述

### 1.1 设计目标
冰/火器官体系是一个基于温度系统的器官协同机制，通过不同温度器官的搭配产生策略性的游戏体验。玩家需要在冰火器官之间寻找平衡，或者专注于单一温度体系以获得独特效果。

### 1.2 核心设计原则
- **非惩罚性**：不使用器官掉落机制，避免给玩家带来负面体验
- **策略性**：鼓励玩家进行器官搭配，提供多种玩法
- **可理解性**：温度系统直观易懂，效果可预测
- **平衡性**：不同温度体系各有优势，避免单一最优解

### 1.3 温度体系分类
- **冰系器官**：温度值为负，提供冰霜效果和控制能力
- **火系器官**：温度值为正，提供火焰效果和爆发伤害
- **中性器官**：温度值为0，不受温度系统影响
- **特殊器官**：具有独特的温度交互机制

## 2. 核心机制设计

### 2.1 温度字段定义
每个冰/火系器官具有基础温度值：
- 冰龙系器官：温度 = -1
- 火龙系器官：温度 = +1
- 电龙系器官：温度 = +0.5（特殊性质）
- 王国系器官：温度 = -2（冰霜）/ +2（火焰）
- 悚怖系器官：温度 = -1
- 浮霜系器官：温度 = -无情等级

### 2.2 全局温度
**定义**：胸腔内所有器官温度值的总和

**计算公式**：
```
全局温度 = Σ(单个器官温度值)
```

**示例**：
- 8个冰龙肌肉（温度-1）+ 1个冰龙心（温度-1）= 全局温度-9
- 4个冰龙器官（温度-1）+ 4个火龙器官（温度+1）= 全局温度0

### 2.3 局部温度

**胸腔网格结构定义**：
- Chest Cavity Beyond 使用 **2D 网格**系统，不是3D结构
- 网格大小：通常是 6×9（可根据具体配置变化）
- 每个器官占据一个或多个网格位置
- 器官之间有明确的相对位置关系

**局部温度计算规则**：

**标准计算范围**：
- 使用 **曼哈顿距离**（Manhattan Distance）
- 计算范围：器官周围 **曼哈顿距离 ≤ 1** 的所有器官
- 等效于：上下左右相邻的4个器官 + 对角相邻的4个器官 = 最多8个邻居器官

**计算公式**：
```
局部温度 = Σ(曼哈顿距离≤1范围内所有器官的基础温度值)
```

**特殊情况处理**：

1. **边缘器官计算**：
   - 对于网格边缘的器官，只计算实际存在的器官
   - 示例：角落位置最多只有3个邻居（右、下、右下）
   - 不需要特殊处理，自然计算实际存在的器官温度总和

2. **核心器官扩展范围**：
   - 心脏、宝玉等核心器官：计算范围扩大到 **曼哈顿距离 ≤ 2**
   - 最多包含周围24个器官位置（5×5范围减去中心位置）
   - 这种扩展在器官的数据配置中定义，不是默认行为

3. **多位置器官处理**：
   - 如果某个器官占据多个网格位置（如大型器官）
   - 该器官的温度会被计算到所有相邻器官的局部温度中
   - 该器官自身的局部温度 = 所有相邻器官温度的平均值

**距离度量选择**：
- **使用曼哈顿距离**（而非欧几里得距离）
- 原因：在网格系统中，曼哈顿距离更符合实际的"相邻"概念
- 曼哈顿距离 = |dx| + |dy|，其中 dx, dy 是网格坐标差值
- 示例：
  - 直角相邻（右、左、上、下）：距离 = 1
  - 对角相邻（右上、右下、左上、左下）：距离 = 2
  - 标准3×3范围 = 曼哈顿距离 ≤ 2

### 2.4 温度状态（替代原有"稳定存在"机制）

#### 2.4.1 三种温度状态
替代原有的掉落机制，我们引入三种温度状态，影响器官的效率而非存在性：

**活跃状态（Active）**
- 条件：全局温度和局部温度都在器官的舒适范围内
- 效果：器官提供100%的属性加成和技能效果

**抑制状态（Suppressed）**
- 条件：全局温度或局部温度超出舒适范围，但在容忍范围内
- 效果：器官提供50%的属性加成和技能效果，并显示视觉提示（器官图标变暗）

**休眠状态（Dormant）**
- 条件：全局温度和局部温度都严重超出舒适范围
- 效果：器官提供25%的属性加成，技能效果完全失效，显示明显的视觉提示（器官图标灰色化）

#### 2.4.2 舒适范围定义
不同器官有不同的舒适范围：

**冰系器官舒适范围**：
- 完全舒适：全局温度 ≤ -4
- 轻微不适：-4 < 全局温度 ≤ 0
- 严重不适：全局温度 > 0

**火系器官舒适范围**：
- 完全舒适：全局温度 ≥ +4
- 轻微不适：0 ≤ 全局温度 < +4
- 严重不适：全局温度 < 0

**中性/特殊器官舒适范围**：
- 根据具体器官特性单独定义

#### 2.4.3 局部温度修正（独立于全局温度）

为了避免循环依赖，局部温度修正采用**独立计算**方式，不改变器官的基础状态。

**温度敏感器官**（如心脏、宝玉）：
- 器官的基础效率由**全局温度**单独决定（见2.4.1）
- 局部温度提供**额外的属性修正**，不影响器官状态判定

**计算方式**：
```
基础效率 = 根据全局温度判定（100% / 50% / 25%）
局部修正系数 = 根据局部温度计算
最终效率 = 基础效率 × 局部修正系数
```

**局部修正规则**：

**冰系器官**：
- 局部温度 ≤ -4：修正系数 = 1.0 + |局部温度| × 0.05（最高 +50%）
- -4 < 局部温度 ≤ 0：修正系数 = 1.0
- 局部温度 > 0：修正系数 = 1.0 - 局部温度 × 0.1（最低 -50%）

**火系器官**：
- 局部温度 ≥ +4：修正系数 = 1.0 + 局部温度 × 0.05（最高 +50%）
- 0 ≤ 局部温度 < +4：修正系数 = 1.0
- 局部温度 < 0：修正系数 = 1.0 - |局部温度| × 0.1（最低 -50%）

**中性器官**：
- 不受局部温度影响，修正系数始终为 1.0

**示例**：
冰龙心在全局温度 -9，局部温度 -8 时：
- 基础效率：100%（全局温度 ≤ -4，活跃状态）
- 局部修正：1.0 + 8 × 0.05 = 1.4
- 最终效率：100% × 1.4 = 140%

冰龙心在全局温度 +2，局部温度 -8 时：
- 基础效率：25%（全局温度 > 0，休眠状态）
- 局部修正：1.0 + 8 × 0.05 = 1.4
- 最终效率：25% × 1.4 = 35%

**关键设计原则**：
- 局部温度只提供属性修正，不改变器官状态
- 避免了"全局温度决定状态，局部温度又影响全局温度"的循环依赖
- 判定流程清晰：全局温度 → 基础状态 → 局部修正 → 最终效率

### 2.5 结算流程

#### 2.5.1 温度判定优先级（避免循环依赖）

为了确保温度系统不会产生循环依赖，我们采用**严格的分层判定**：

**第一层：全局温度计算**
```
实际全局温度 = Σ(所有器官的基础温度值)
```
- 这个计算不考虑任何特殊器官效果
- 是整个温度系统的底层基础数据

**第二层：全局温度修正（特殊器官）**
```
有效全局温度 = 应用Malkuth等特殊器官的修正
```
- 如果装备了Malkuth，有效全局温度 = 0
- 否则，有效全局温度 = 实际全局温度
- 这一层的输出不依赖于局部温度

**第三层：器官状态判定**
```
器官基础状态 = 根据有效全局温度判定
```
- 只使用有效全局温度，不使用局部温度
- 判定结果：活跃（100%）/ 抑制（50%）/ 休眠（25%）
- 这一步确定了器官的"基础效率"

**第四层：局部温度计算**
```
实际局部温度 = Σ(曼哈顿距离≤1范围内器官的基础温度值)
有效局部温度 = 应用Malkuth等特殊器官的修正
```
- 局部温度的计算不影响全局温度
- 局部温度只用于属性修正，不改变器官状态

**第五层：最终效率计算**
```
最终效率 = 器官基础状态效率 × 局部温度修正系数
```
- 局部温度修正系数见 2.4.3
- 最终效率用于属性加成计算

**关键原则**：
- **全局温度 → 局部温度**（单向依赖）
- **状态判定 → 属性修正**（分层计算）
- **没有反向影响**：局部温度不会影响全局温度，属性修正不会改变状态

#### 2.5.2 实时结算（每tick执行）

**高频更新**（每tick执行，但使用缓存）：
1. **温度缓存读取**：从缓存中读取预计算的温度值
2. **状态判定**：根据有效全局温度确定器官基础状态
3. **效率计算**：应用局部温度修正，计算最终效率
4. **效果触发**：触发温度相关的被动效果和技能

**低频更新**（每秒执行一次）：
1. **缓存验证**：检查器官配置是否变化
2. **缓存更新**：如果配置变化，重新计算温度缓存

#### 2.5.3 胸腔关闭时结算（chestCavityCloseEvent）

**完整重新计算**：
1. **全局温度重算**：
   - 遍历所有器官，计算实际全局温度
   - 检查特殊器官（如Malkuth），计算有效全局温度
   - 更新全局温度缓存

2. **局部温度重算**：
   - 为每个器官计算实际局部温度（基于网格位置）
   - 检查特殊器官，计算有效局部温度
   - 更新所有器官的局部温度缓存

3. **器官状态更新**：
   - 根据有效全局温度更新所有器官的基础状态
   - 计算并存储每个器官的最终效率

4. **特殊器官触发**：
   - 触发Malkuth等特殊器官的被动效果
   - 更新温度平衡加成等特殊机制

5. **UI刷新**：
   - 更新胸腔界面的温度显示
   - 更新器官状态标识

**性能优化**：
- 胸腔关闭时进行完整计算，之后使用缓存
- 只有器官配置变化时才重新计算
- 使用事件监听器检测器官变化

#### 2.5.4 伤害/攻击结算

**攻击时结算**：
1. **检查温度加成**：读取武器器官的最终效率
2. **应用攻击增强**：根据温度类型应用冰冻/燃烧效果
3. **触发特殊效果**：如链电、反弹等

**受伤时结算**：
1. **检查防御加成**：读取防御器官的最终效率
2. **应用防御效果**：如冰霜护盾、烈焰护甲等
3. **触发反击效果**：如缓速、燃烧等

#### 2.5.5 结算流程图

```
器官配置变化（胸腔关闭/器官移除）
    ↓
[第一层] 计算实际全局温度 = Σ(器官基础温度)
    ↓
[第二层] 应用特殊器官修正 → 有效全局温度
    ↓
[第三层] 判定器官基础状态（活跃/抑制/休眠）
    ↓
[第四层] 计算实际局部温度 → 有效局部温度
    ↓
[第五层] 应用局部修正 → 最终效率
    ↓
缓存所有计算结果
    ↓
运行时使用缓存，不重复计算
```

**数据流向**：
- 输入：器官配置（器官类型、数量、位置）
- 输出：每个器官的最终效率和状态
- 特点：单向流动，无循环依赖

## 3. 器官详细设计

### 3.1 冰龙系器官

#### 3.1.1 冰龙心脏（ice_dragon_heart）
**基本信息**：
- 标签：#心脏 #冰系 #核心器官
- 基础温度：-1
- 限制：同时只能装备1个心脏类器官

**基础属性**：
- +2 健康

**温度相关属性**：
- 活跃状态（全局温度≤-4）：+4 额外健康
- 抑制状态（-4<全局温度≤0）：+2 额外健康
- 休眠状态（全局温度>0）：+1 额外健康

**局部温度增益**：
- 效率受局部温度修正（温度敏感器官）
- 自身局部温度视为周围3×3范围的温度总和
- 每点局部负温度额外提供0.25健康值

**被动效果**：
- 寒霜护体：受到近战伤害时，有20%几率对攻击者施加缓速II（2秒）
- 冰霜抗性：+15%冰霜伤害抗性

**技能**：
- 无主动技能（作为被动增益器官）

**代码示例**：
```java
@Override
public Multimap<Holder<Attribute>, AttributeModifier> getAttributeModifiers(ChestCavitySlotContext context) {
    var modifiers = HashMultimap.create();
    float globalTemp = TemperatureSystem.getGlobalTemperature(context.entity());
    float localTemp = TemperatureSystem.getLocalTemperature(context.slot(), context.entity());

    // 基础健康
    modifiers.put(InitAttribute.HEALTH, new AttributeModifier(BASE_HEALTH_UUID, 2, Operation.ADD_VALUE));

    // 温度状态加成
    float efficiency = TemperatureSystem.getEfficiency("ice", globalTemp);
    modifiers.put(InitAttribute.HEALTH, new AttributeModifier(TEMP_HEALTH_UUID, 4 * efficiency, Operation.ADD_VALUE));

    // 局部温度加成
    if (efficiency > 0.5f) {
        float localBonus = Math.max(0, -localTemp * 0.25f);
        modifiers.put(InitAttribute.HEALTH, new AttributeModifier(LOCAL_HEALTH_UUID, localBonus, Operation.ADD_VALUE));
    }

    return modifiers;
}
```

### 3.4 王国系器官

#### 3.4.1 Malkuth（王国）（malkuth）
**基本信息**：
- 标签：#特殊 #核心器官 #温度调节器
- 基础温度：0
- 限制：同时只能装备1个

**特殊机制：温度平衡协同**

**设计理念变更**：
原设计中的"重写所有器官局部温度"机制需要修改 Chest Cavity Beyond 的核心代码，违反了项目范围约束。因此重新设计为一个**独立的温度平衡加成系统**，完全在 Who-Am-I-Core 工作区内实现。

**新机制：温度平衡加成**

**被动效果**：

1. **全局温度中和**：
   - 装备 Malkuth 时，全局温度始终视为 **0**
   - 这不会改变器官的实际温度值，只是在判定器官状态时使用中和后的温度
   - 实现方式：在温度系统查询时，如果装备了 Malkuth，返回中和后的全局温度

2. **局部温度平衡加成**：
   - 计算所有冰火器官的"温度强度"：
     ```
     冰系强度 = 所有冰系器官温度绝对值总和
     火系强度 = 所有火系器官温度绝对值总和
     总温度强度 = 冰系强度 + 火系强度
     ```
   - 所有冰系器官获得额外的"虚拟局部温度"：-总温度强度
   - 所有火系器官获得额外的"虚拟局部温度"：+总温度强度
   - 这个虚拟局部温度只用于属性计算，不改变实际的网格布局

**实现细节**：

**温度查询API扩展**（在 Who-Am-I-Core 中实现）：
```java
public class TemperatureSystem {
    // 获取用于判定的全局温度（考虑Malkuth）
    public static float getEffectiveGlobalTemperature(LivingEntity entity) {
        float actualTemp = calculateActualGlobalTemperature(entity);
        if (hasMalkuthEquipped(entity)) {
            return 0; // Malkuth将全局温度中和为0
        }
        return actualTemp;
    }

    // 获取用于属性计算的局部温度（考虑Malkuth）
    public static float getEffectiveLocalTemperature(Organ organ, LivingEntity entity) {
        float actualTemp = calculateActualLocalTemperature(organ, entity);
        if (hasMalkuthEquipped(entity)) {
            float totalIntensity = calculateTotalTemperatureIntensity(entity);
            if (organ.isIceType()) {
                return -totalIntensity; // 冰系获得负的总温度强度
            } else if (organ.isFireType()) {
                return totalIntensity;  // 火系获得正的总温度强度
            }
        }
        return actualTemp;
    }

    // 计算总温度强度
    private static float calculateTotalTemperatureIntensity(LivingEntity entity) {
        float iceIntensity = 0;
        float fireIntensity = 0;
        for (Organ organ : getAllOrgans(entity)) {
            if (organ.isIceType()) {
                iceIntensity += Math.abs(organ.getBaseTemperature());
            } else if (organ.isFireType()) {
                fireIntensity += Math.abs(organ.getBaseTemperature());
            }
        }
        return iceIntensity + fireIntensity;
    }
}
```

**效果说明**：

1. **冰火共存**：
   - 装备 Malkuth 后，冰系和火系器官都能达到活跃状态
   - 因为全局温度被中和为0，所有器官都不会受到抑制

2. **局部协同增强**：
   - 所有冰系器官都获得与"总温度强度"成正比的虚拟局部温度
   - 所有火系器官也获得相同的虚拟局部温度
   - 冰火器官越多，双方的局部协同效果都越强

**示例**：

**配置**：
- 4个冰龙器官（温度-1）+ 4个火龙器官（温度+1）+ Malkuth

**计算**：
- 实际全局温度：4×(-1) + 4×(+1) = 0
- 有效全局温度：0（Malkuth中和）
- 冰系强度：4
- 火系强度：4
- 总温度强度：8

**效果**：
- 所有冰龙器官的有效局部温度：-8
- 所有火龙器官的有效局部温度：+8
- 冰龙心和火龙心都获得最大协同效果
- 所有器官都是活跃状态（全局温度为0，但Malkuth特殊处理）

**另一个示例**：

**配置**：
- 6个冰龙器官（温度-1）+ 2个火龙器官（温度+1）+ Malkuth

**计算**：
- 实际全局温度：6×(-1) + 2×(+1) = -4
- 有效全局温度：0（Malkuth中和）
- 冰系强度：6
- 火系强度：2
- 总温度强度：8

**效果**：
- 所有冰龙器官的有效局部温度：-8
- 所有火龙器官的有效局部温度：+8
- 即使冰火数量不平衡，双方仍获得相同的协同加成

**优势**：
- 不需要修改 CCB 核心代码
- 完全在 Who-Am-I-Core 工作区内实现
- 通过API层实现温度重写，而不是修改底层器官数据
- 实现简单，性能开销小

**限制和平衡**：
- 装备Malkuth时，无法使用任何主动吐息技能
- 基础属性降低20%（作为平衡）
- Malkuth 自身不提供任何属性加成（温度为0）
- 需要投入大量器官才能发挥效果（至少4+4配置）

**技术实现要点**：
- 使用事件拦截：在器官查询温度时，检查是否装备了Malkuth
- 缓存优化：缓存总温度强度，避免每tick重新计算
- 仅在胸腔关闭时重新计算，运行时使用缓存值
- 不修改任何 CCB 的器官数据结构，只在外层包裹逻辑

## 6. 实施建议

### 6.1 技术实现

#### 6.1.1 温度系统API设计

**核心API接口**（在 Who-Am-I-Core 中实现）：

```java
/**
 * 温度系统核心类
 * 负责所有温度相关的计算和查询
 * 完全独立于CCB核心代码，通过外部API实现
 */
public class TemperatureSystem {

    // ==================== 基础温度查询 ====================

    /**
     * 获取实际全局温度（不考虑任何修正）
     * @param entity 实体
     * @return 所有器官基础温度的总和
     */
    public static float getActualGlobalTemperature(LivingEntity entity);

    /**
     * 获取有效全局温度（考虑Malkuth等特殊器官）
     * @param entity 实体
     * @return 用于状态判定的全局温度
     */
    public static float getEffectiveGlobalTemperature(LivingEntity entity);

    /**
     * 获取器官的实际局部温度（不考虑任何修正）
     * @param organ 器官实例
     * @param entity 实体
     * @return 器官周围曼哈顿距离≤1范围内的器官温度总和
     */
    public static float getActualLocalTemperature(Organ organ, LivingEntity entity);

    /**
     * 获取器官的有效局部温度（考虑Malkuth等特殊器官）
     * @param organ 器官实例
     * @param entity 实体
     * @return 用于属性计算的局部温度
     */
    public static float getEffectiveLocalTemperature(Organ organ, LivingEntity entity);

    // ==================== 状态判定API ====================

    /**
     * 获取器官的基础状态（由全局温度决定）
     * @param organ 器官实例
     * @param entity 实体
     * @return ACTIVE(100%) / SUPPRESSED(50%) / DORMANT(25%)
     */
    public static TemperatureState getOrganBaseState(Organ organ, LivingEntity entity);

    /**
     * 获取器官的最终效率（基础状态 × 局部修正）
     * @param organ 器官实例
     * @param entity 实体
     * @return 0.0 ~ 1.5 之间的效率值
     */
    public static float getOrganFinalEfficiency(Organ organ, LivingEntity entity);

    /**
     * 获取器官的基础效率（不考虑局部修正）
     * @param state 器官状态
     * @return 1.0 (活跃) / 0.5 (抑制) / 0.25 (休眠)
     */
    public static float getBaseEfficiency(TemperatureState state);

    /**
     * 获取局部温度修正系数
     * @param organ 器官实例
     * @param effectiveLocalTemp 有效局部温度
     * @return 修正系数（如 1.4 表示 +40%）
     */
    public static float getLocalModifier(Organ organ, float effectiveLocalTemp);

    // ==================== 特殊器官API ====================

    /**
     * 检查实体是否装备了Malkuth
     * @param entity 实体
     * @return true如果装备了Malkuth
     */
    public static boolean hasMalkuthEquipped(LivingEntity entity);

    /**
     * 计算总温度强度（用于Malkuth机制）
     * @param entity 实体
     * @return 所有冰火器官温度绝对值的总和
     */
    public static float calculateTotalTemperatureIntensity(LivingEntity entity);

    // ==================== 缓存管理API ====================

    /**
     * 强制重新计算所有温度缓存
     * 在胸腔关闭或器官配置变化时调用
     * @param entity 实体
     */
    public static void recalculateTemperatureCache(LivingEntity entity);

    /**
     * 验证缓存是否有效
     * @param entity 实体
     * @return true如果缓存有效
     */
    public static boolean isCacheValid(LivingEntity entity);

    // ==================== 数据结构 ====================

    /**
     * 温度状态枚举
     */
    public enum TemperatureState {
        ACTIVE(1.0f),      // 活跃：100%效率
        SUPPRESSED(0.5f),  // 抑制：50%效率
        DORMANT(0.25f);    // 休眠：25%效率

        private final float baseEfficiency;

        TemperatureState(float baseEfficiency) {
            this.baseEfficiency = baseEfficiency;
        }

        public float getBaseEfficiency() {
            return baseEfficiency;
        }
    }

    /**
     * 温度缓存数据
     */
    public static class TemperatureCache {
        public float actualGlobalTemperature;
        public float effectiveGlobalTemperature;
        public Map<Organ, Float> actualLocalTemperatures;
        public Map<Organ, Float> effectiveLocalTemperatures;
        public Map<Organ, TemperatureState> organStates;
        public Map<Organ, Float> organEfficiencies;
        public long lastUpdateTime;
        public int organConfigHash; // 用于检测配置变化
    }
}
```

#### 6.1.2 实现架构

**分层架构**（避免循环依赖）：

```
┌─────────────────────────────────────┐
│   器官层（Organ Implementation）     │
│   - 调用 TemperatureSystem API       │
│   - 获取效率，计算属性加成             │
└─────────────────────────────────────┘
              ↓
┌─────────────────────────────────────┐
│   温度系统层（TemperatureSystem）     │
│   - 提供所有温度相关的查询API          │
│   - 管理温度缓存                      │
│   - 协调特殊器官机制                  │
└─────────────────────────────────────┘
              ↓
┌─────────────────────────────────────┐
│   数据层（Data Layer）                │
│   - 读取器官配置                      │
│   - 访问胸腔网格数据（通过CCB API）   │
│   - 管理缓存存储                      │
└─────────────────────────────────────┘
```

**关键设计决策**：

1. **单向数据流**：
   - 器官层 → 温度系统层 → 数据层
   - 不允许反向修改，避免循环依赖

2. **缓存优先**：
   - 所有计算结果缓存
   - 只在配置变化时重新计算
   - 运行时使用缓存，性能开销极小

3. **API封装**：
   - 所有复杂逻辑封装在 TemperatureSystem 中
   - 器官实现只需调用简单API
   - 便于维护和扩展

4. **特殊器官处理**：
   - Malkuth 等特殊器官在 API 层面处理
   - 不修改 CCB 的底层器官数据
   - 通过"有效温度"概念实现修正

#### 6.1.2 器官数据扩展
在器官数据中添加温度字段：

```java
public class OrganData {

    private String temperatureType; // 温度类型（ice/fire/neutral）
    private float comfortMin;       // 舒适范围最小值
    private float comfortMax;       // 舒适范围最大值
    private boolean temperatureSensitive; // 是否温度敏感
}
```

#### 6.1.3 事件处理
在合适的事件中调用温度系统：

```java
// 每tick更新温度缓存
@SubscribeEvent
public void onEntityTick(LivingEvent.LivingTickEvent event) {
    if (event.getEntity().tickCount % 20 == 0) { // 每秒更新一次
        TemperatureSystem.updateTemperatureCache(event.getEntity());
    }
}

// 胸腔关闭时重新计算温度
@SubscribeEvent
public void onChestCavityClose(ChestCavityCloseEvent event) {
    TemperatureSystem.recalculateTemperature(event.getEntity());
}
```
